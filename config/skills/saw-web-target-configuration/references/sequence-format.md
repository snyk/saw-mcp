# Login Sequence JSON Format

The sequence format (based on the [Snyk API & Web Sequence Recorder](https://github.com/Probely/sequence-recorder)):

**IMPORTANT: Use Custom Fields; Use Credentials Manager by Default**

**Always use custom field placeholders for username and password** instead of hardcoding them in the sequence. **Use the credentials manager by default** for the password. If the user explicitly declines, inline values in custom_field_mappings are allowed.

- Use `[CUSTOM_USERNAME]` placeholder for the username field — map to inline `value` in custom_field_mappings (not sensitive)
- Use `[CUSTOM_PASSWORD]` placeholder for the password field. Create a credential via `probely_create_credential` with `is_sensitive=True` and pass its `uri` (e.g. `credentials://xxxx`) as the `value` in custom_field_mappings. When **multiple targets share the same credential** and it already exists as sensitive, prompt the user to deobfuscate it to allow reuse.
- **2FA OTP codes should remain hardcoded** in the sequence (store the TOTP seed via credential manager in step 3)
- **Always add `"powered_by": "saw mcp"` to the first `goto` step** of every login sequence you create (tags the sequence as generated by this MCP).
- **If the login opens in a popup window** (e.g. a `window.open(...)` triggered by a "login" button/link), add `"allow_popups": true` to the first `goto` step so the replayer permits the popup to open. See **Popup-Based Logins** below.
- **Always precede every `fill_value`/`bfill_value` with a `click` on the same field** to focus the cursor in the input first. Some pages (e.g. framework-driven or shadow-DOM forms) only accept input on a focused field, so the fill silently fails without a preceding click. The `click` targets the same `css`/`xpath` as the fill, with an empty `value`. (Canvas logins already do this via `bclick` before `bfill_value`.)

Example sequence with custom fields:

```json
[
  {
    "type": "goto",
    "timestamp": 1234567890000,
    "url": "https://app.example.com/login",
    "windowWidth": 1280,
    "windowHeight": 720,
    "urlType": "force",
    "powered_by": "saw mcp"
  },
  { 
    "type": "click",
    "timestamp": 1234567891000,
    "css": "input[name='email']",
    "xpath": "//*[@name='email']",
    "value": "",
    "frame": null
  },
  {
    "type": "fill_value",
    "timestamp": 1234567892000,
    "css": "input[name='email']",
    "xpath": "//*[@name='email']",
    "value": "[CUSTOM_USERNAME]",
    "frame": null
  },
  { 
    "type": "click",
    "timestamp": 1234567893000,
    "css": "input[name='password']",
    "xpath": "/html/body/form/input[2]",
    "value": "",
    "frame": null
  },
  {
    "type": "fill_value",
    "timestamp": 1234567894000,
    "css": "input[name='password']",
    "xpath": "/html/body/form/input[2]",
    "value": "[CUSTOM_PASSWORD]",
    "frame": null
  },
  {
    "type": "click",
    "timestamp": 1234567895000,
    "css": "button[name='btnSubmit']",
    "xpath": "/html/body/form/button",
    "value": "Sign In",
    "frame": null
  }
]
```

**For 2FA**, use the `otp_code` returned by `probely_configure_2fa_totp` **hardcoded** in the sequence (do NOT use a custom field for OTP):
```json
{
  "type": "fill_value",
  "timestamp": 1234567896000,
  "css": "#otp",
  "xpath": "//*[@id='otp']",
  "value": "829182",
  "frame": null
}
```
Probely will automatically convert `fill_value` entries matching the configured OTP code to `fill_otp` type at scan time.

## Sequence Event Types

The canonical, always-up-to-date list of every supported event type is maintained in the
recorder repo's [`OUTPUT-EXAMPLE.md`](https://github.com/Probely/sequence-recorder/blob/main/OUTPUT-EXAMPLE.md).
The table below mirrors it — consult that file if in doubt.

| Type | Description | Key fields |
|------|-------------|------------|
| `goto` | Navigate to a URL (first step in every recording) | `url`, `windowWidth`, `windowHeight`, `urlType`, `powered_by` (set to `"saw mcp"` on the first step), `allow_popups` (set to `true` on the first step for popup-based logins) |
| `click` | Standard left click on a DOM element | `css`, `xpath`, `value` (button text, ≤20 chars), `frame` |
| `bclick` | Click on a **canvas surface** — includes `coords` (`x`, `y`, `width`, `height`). Use for any `<canvas>`-rendered UI (e.g. Flutter web, game engines, custom canvas widgets). May include `shadow_host_css` when the canvas is inside a shadow DOM | `css`, `xpath`, `coords`, `value`, `frame`, `shadow_host_css?` |
| `dblclick` | Double click on an element | `css`, `xpath`, `value`, `frame` |
| `mouseover` | Hover over an element (debounced 500 ms) | `css`, `xpath`, `value`, `frame` |
| `fill_value` | Value entered into an `<input>`/`<textarea>` (captured on blur or Enter) | `css`, `xpath`, `value`, `frame` |
| `bfill_value` | **Buffered fill** — keystroke-reconstructed value when the DOM `.value` stays empty (virtual keyboards, frameworks that clear the field, or canvas-rendered forms). For canvas inputs, carries `coords` from the preceding `bclick` | `css`, `xpath`, `value`, `frame`, `coords?` |
| `fill_otp` | Enter OTP code (Probely auto-converts a matching `fill_value`) | `css`, `xpath`, `value` (OTP code), `frame` |
| `press_key` | Key press (currently Enter only, `value: 13`) emitted after a fill on Enter | `css`, `xpath`, `value` (keyCode), `frame` |
| `change` (`check`) | Checkbox/radio toggled | `css`, `xpath`, `subtype: "check"`, `checked`, `frame` |
| `change` (`select`) | Single `<select>` changed | `css`, `xpath`, `subtype: "select"`, `selected` (index), `value`, `frame` |
| `change` (`select_multi`) | Multi-select `<select>` changed | `css`, `xpath`, `subtype: "select_multi"`, `selected` (bool array), `value`, `frame` |

### The `frame` field (iframes)

`frame` is the CSS selector of the containing iframe, or empty string / `null` at the top
level. For nested iframes, selectors are joined outermost-to-innermost with ` >>> `
(e.g. `#outer-iframe >>> #inner-iframe`).

## Canvas-Rendered Logins (`bclick` + `bfill_value`)

Some apps **paint** the username field, password field, and submit button onto a
`<canvas>` element (for example Flutter web, game engines, or custom canvas widgets).
Clicks are dispatched by the page's own handler using pixel coordinates, so there is
**no clickable DOM button** — `scripts/inspect-login-form.js` reports `submit: null` and
flags a `canvas` surface.

Handle these with the recorder's canvas events:

- **`bclick`** — a click on the canvas at pixel `coords` **relative to the canvas's
  bounding rect**. `coords` also carries the canvas `width`/`height` so Probely can scale
  the click if the rendered size differs at scan time. Use one `bclick` to focus each
  field and one to press the submit button.
- **`bfill_value`** — buffered text fill, used when typing goes to a canvas/virtual input
  whose DOM `.value` stays empty. If the page keeps a real (often hidden) `<input>` that
  receives the keystrokes (its `.value` actually gets set), use a normal `fill_value` on
  that input instead — it is more robust.

### How to find the coordinates

Canvas pages usually keep hidden `<input>` elements plus a `<script>` that describes the
layout (field/button rectangles). **Read the page script or take a screenshot** to locate
each rectangle, then target its **center**. Coordinates are canvas-relative:
`x`/`y` = the center within the canvas, and `width`/`height` = the canvas's
`getBoundingClientRect()` size.

### Example: canvas login with hidden inputs

The site draws Username / Password / SIGN IN on a 380×520 canvas (`#flutterCanvas`) but
keeps hidden `#username`/`#password` inputs that receive real keystrokes — so `fill_value`
works for the inputs and `bclick` presses the painted button:

```json
[
  { "type": "goto", "timestamp": 1700000000000, "url": "https://app.example.com/login", "windowWidth": 1280, "windowHeight": 720, "urlType": "force", "powered_by": "saw mcp" },
  { "type": "bclick", "timestamp": 1700000001000, "css": "#flutterCanvas", "xpath": "//*[@id=\"flutterCanvas\"]", "coords": { "x": 190, "y": 204, "width": 380, "height": 520 }, "value": "", "frame": null },
  { "type": "fill_value", "timestamp": 1700000002000, "css": "input[name=\"username\"]", "xpath": "//*[@id=\"username\"]", "value": "[CUSTOM_USERNAME]", "frame": null },
  { "type": "bclick", "timestamp": 1700000003000, "css": "#flutterCanvas", "xpath": "//*[@id=\"flutterCanvas\"]", "coords": { "x": 190, "y": 274, "width": 380, "height": 520 }, "value": "", "frame": null },
  { "type": "fill_value", "timestamp": 1700000004000, "css": "input[name=\"password\"]", "xpath": "//*[@id=\"password\"]", "value": "[CUSTOM_PASSWORD]", "frame": null },
  { "type": "bclick", "timestamp": 1700000005000, "css": "#flutterCanvas", "xpath": "//*[@id=\"flutterCanvas\"]", "coords": { "x": 190, "y": 354, "width": 380, "height": 520 }, "value": "SIGN IN", "frame": null }
]
```

If typing does **not** set a hidden input's `.value` (pure canvas input), replace the
`fill_value` entries with `bfill_value` on the canvas selector, carrying the same `coords`
as the preceding `bclick`.

## Popup-Based Logins (`allow_popups`)

Some apps open their login form in a **popup window** rather than inline — a button or
link runs `window.open(...)` (often to a separate URL such as `popup.php`), and the
username/password fields live in that new window. Directly navigating to the popup URL
frequently fails (it may redirect back to the landing page when opened outside the popup
context), so the sequence must **click the trigger to open the popup**, then fill the
fields in it.

By default the replayer blocks popups, so the popup never opens and the login fails. To
allow it, **add `"allow_popups": true` to the first `goto` step** (alongside
`powered_by`). Record the flow as usual: `goto` the landing page → `click` the element
that opens the popup → `click`/`fill_value` the username and password inside the popup →
`click` the submit button. The popup fields are addressed with normal `css`/`xpath`
selectors (`frame` stays `null` — a popup is a separate window, not an iframe).

For **logout detection**, remember the login-form selectors only exist inside the popup,
not on the landing/check-session URL. Pick a detector that is present on the
check-session URL only when logged out — commonly the button/link that opens the popup
(e.g. `sel: #b_open_login_popup`).

### Example: popup login triggered by a button

The landing page has a `#open_login` button that opens `popup.php` containing the
`#formlogin` form:

```json
[
  { "type": "goto", "timestamp": 1700000000000, "url": "https://app.example.com/", "windowWidth": 1280, "windowHeight": 720, "urlType": "force", "powered_by": "saw mcp", "allow_popups": true },
  { "type": "click", "timestamp": 1700000001000, "css": "#open_login", "xpath": "//*[@id='open_login']", "value": "Click to login", "frame": null },
  { "type": "click", "timestamp": 1700000002000, "css": "input[name='username']", "xpath": "//*[@name='username']", "value": "", "frame": null },
  { "type": "fill_value", "timestamp": 1700000003000, "css": "input[name='username']", "xpath": "//*[@name='username']", "value": "[CUSTOM_USERNAME]", "frame": null },
  { "type": "click", "timestamp": 1700000004000, "css": "input[name='password']", "xpath": "//*[@name='password']", "value": "", "frame": null },
  { "type": "fill_value", "timestamp": 1700000005000, "css": "input[name='password']", "xpath": "//*[@name='password']", "value": "[CUSTOM_PASSWORD]", "frame": null },
  { "type": "click", "timestamp": 1700000006000, "css": "#formlogin input[type='submit']", "xpath": "//form[@id='formlogin']//input[@type='submit']", "value": "Login", "frame": null }
]
```

## Shadow DOM Inputs (`/html/node/shadow`)

Some apps put the real `<input>` inside an **open shadow root** — commonly via
form-associated custom elements (e.g. `<shadow-input name="username">` that renders an
`<input>` in its shadow DOM and reports its value with `ElementInternals.setFormValue()`).
`document.querySelector` cannot see these inputs, so `scripts/inspect-login-form.js`
reports `step: "shadow_dom"`.

The recorder handles these with a specific, non-obvious contract — **follow it exactly**:

- **Target the INNER element, not the host.** The recorder reads `event.composedPath()`
  and records the innermost element (the actual `<input>`), then builds a simple selector
  from that element alone via `getCustomSelector`.
- **Selectors have no host/form prefix.** The inner input usually has **no `id` and no
  `name`** (the `name` lives on the host custom element), and `closest('form')` /
  `closest('body')` do **not** cross the shadow boundary — so the selector collapses to
  just `input[type="text"]`, `input[type="password"]`, etc.
- **`xpath` should be a real, attribute-based XPath for the inner element.** Probely's
  replayer can evaluate an XPath that pierces the shadow root, so prefer a concrete query
  built from the inner element's attributes, e.g.
  `//input[@name='username' and @autocomplete='username']` or `//input[@type='password']`.
  The raw recorder emits the sentinel `"/html/node/shadow"` (an XPath can't natively
  address a shadow node); that sentinel still works as a **fallback** when the inner
  element exposes no distinguishing attributes, but a real XPath is more robust.
- **No `shadow_host_css` for fills.** That field is emitted **only** for `bclick` (canvas
  in shadow), never for `fill_value`. Shadow text inputs carry only the inner-element
  selector plus the sentinel xpath.

### ⚠️ Selectors must be UNIQUE across all shadow roots

Each shadow root is an **isolated scope**, so two different hosts can contain
**identical** inner markup — e.g. `<shadow-input name="username">` and
`<shadow-input name="password">` may both render `<input id="field" name="field">`
inside their shadow roots. Because the replayer resolves the `css`/`xpath` with a
**shadow-piercing search across the whole page**, a selector that isn't globally unique
(e.g. bare `input`, or an `id`/`name` that repeats in another shadow root) will match
**multiple** elements and the replayer may fill the **wrong** one.

**Always find a selector/XPath that uniquely identifies each field.** In priority order:

1. A distinguishing attribute on the inner element itself — `type` (often enough to tell
   username from password), `autocomplete` (`username` vs `current-password`),
   `placeholder`, `aria-label`, or a differing `name`/`id`.
2. A combination of the above, e.g. `//input[@type='password' and @autocomplete='current-password']`.
3. If the inner elements are genuinely indistinguishable by attributes, disambiguate by
   position across the piercing result (document order), e.g. `(//input)[1]` /
   `(//input)[2]`, and double-check which index maps to which field.

`scripts/inspect-login-form.js` flags this: it adds `ambiguous: true` and a `warning` to
any shadow field whose `selector`/`xpath` also matches another collected shadow element.

### ⚠️ Do NOT use `host descendant` piercing selectors

A selector like `shadow-input[name="username"] input` is **wrong**. A cross-boundary
descendant combinator matches in **no single tree** (the `<input>` is not a light-DOM
descendant of the host, and within any one shadow root the host isn't present), so the
replayer's per-root shadow-piercing search returns nothing and the fill fails. Never use
the host tag, the host's `name`, or a `host … input` combinator for a shadow fill.

### Example: form-associated custom-element login

Username/password are `<shadow-input>` custom elements; the submit `<button>` is in the
light DOM. The correct sequence targets the inner inputs with plain `input[type="…"]`
css selectors and a real attribute-based `xpath` that pierces the shadow root:

```json
[
  { "type": "goto", "timestamp": 1700000000000, "url": "https://app.example.com/login", "windowWidth": 1280, "windowHeight": 720, "urlType": "force", "powered_by": "saw mcp" },
  { "type": "click", "css": "input[type=\"text\"]", "xpath": "//input[@type='text']", "value": "", "frame": "" },
  { "type": "fill_value", "css": "input[type=\"text\"]", "xpath": "//input[@type='text']", "value": "[CUSTOM_USERNAME]", "frame": "" },
  { "type": "click", "css": "input[type=\"password\"]", "xpath": "//input[@type='password']", "value": "", "frame": "" },
  { "type": "fill_value", "css": "input[type=\"password\"]", "xpath": "//input[@type='password']", "value": "[CUSTOM_PASSWORD]", "frame": "" },
  { "type": "click", "css": "form button[type=\"submit\"]", "xpath": "/html/body/div/form/button", "value": "Submit Form", "frame": "" }
]
```

When the inner inputs expose richer attributes, build a more specific XPath, e.g.
`//input[@name='username' and @autocomplete='username']`.

If the framework clears the inner input's `.value` while typing (buffered/virtual input),
use `bfill_value` instead of `fill_value` — the selector/xpath rules are identical.
